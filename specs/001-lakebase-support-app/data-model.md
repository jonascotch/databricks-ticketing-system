# Data Model: Lakebase Support App

All operational ticketing data is stored in Lakebase PostgreSQL.

## Ticket

Represents one support request and maps to the `tickets` table.

| Field | Type / rule | Notes |
|---|---|---|
| `ticket_id` | `UUID`, primary key, generated by the database on creation | Stable identity; not user-editable |
| `title` | `TEXT`, required, trimmed, 1–200 characters | Reject empty or over-limit values |
| `status` | `TEXT`, required, one of `open`, `in_progress`, `resolved`; defaults to `open` | Any of these states may be selected |
| `created_by` | `TEXT`, required | Signed-in Databricks user identity |
| `created_at` | `TIMESTAMPTZ`, required, database generated | Creation time |

Tickets may be listed by creation time, newest first.

## Ticket Message

Represents a message attached to a ticket and maps to the `ticket_messages`
table.

| Field | Type / rule | Notes |
|---|---|---|
| `message_id` | `UUID`, primary key, generated by the database on creation | Stable identity |
| `ticket_id` | `UUID`, required foreign key to `tickets.ticket_id` | Prevents orphan messages |
| `message_text` | `TEXT`, required, trimmed, 1–5000 characters | Reject empty or over-limit values |
| `author` | `TEXT`, required | Signed-in Databricks user identity |
| `created_at` | `TIMESTAMPTZ`, required, database generated | Message creation time |

Messages are displayed oldest first.

## Relationships and lifecycle

- One ticket has zero or more messages; every message belongs to exactly one
  ticket.
- New tickets start in `open`; users may change a ticket to any supported
  status.
- Ticket and message IDs are generated by the database; creator/author
  attribution is recorded by the app and is not supplied by form fields.
- Ticket deletion and message editing/deletion are out of scope.

## Seed data

The seed operation must leave at least three sample tickets, at least two
messages per sample ticket, and at least two different ticket statuses. Seed
records should have stable identifiers and conflict-safe inserts so rerunning
the script does not duplicate records or overwrite later user changes.
